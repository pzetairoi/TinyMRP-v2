  3.2 THE ACTUAL COST, MEASURED

    Three consecutive runs of each scan, from the journal:
      mecs   56.1s  51.5s  52.1s
      test   38.7s  30.8s  30.5s

    Both timers fired at 1786157409.640 and 1786157409.645 - SIX
    MILLISECONDS apart. They are not staggered and they never will be:
    install-backup-job.sh sets RandomizedDelaySec=600, and
    install-nextcloud-scan-job.sh sets nothing at all.

    Duty cycle: 52s + 31s of concurrent work every 300s on two cores.
    Roughly 28% of the machine's wall-clock time, almost always computing
    that nothing has changed.

    One mecs run broken down:
      02:50:10  mount visibility check
      02:50:13  group user discovery
      02:50:39  files_external:scan 1          26s
      02:51:01  files:scan --path=admin/...    22s
      total 51s

    THE SECOND PASS RE-WALKS THE TREE THE FIRST PASS JUST WALKED. Same
    files, once as the external mount and once through the user's view.
    About half the cost, and nobody has ever tested whether dropping it
    changes what appears in the Nextcloud UI. That test is item 3.5.

    Good news the review guessed at and could not confirm: the targeted
    path is working. "files_external:scan --all fallback used: no" and
    "files:scan --all fallback used: no" on every run. The catastrophic
    fallback exists but is not firing.

  3.3 THE IDEA THAT DOES NOT SURVIVE CONTACT WITH THE CODE

    The review proposes that TinyMRP mark the mount dirty on write and
    trigger a targeted scan. The instinct is right. The mechanism cannot
    be built as described:

      TinyMRP HAS NO NEXTCLOUD AWARENESS AT ALL. Grepping the whole of
      app/ for "nextcloud" returns two hits, both in static help HTML.
      The integration lives entirely in deploy/scripts.

      THE APP CANNOT RUN occ. It is a non-root container with no docker
      socket. Mounting the socket to let it exec into the Nextcloud
      container would hand the application root on the host and undo the
      hardening plan in a single line. Not a trade worth making to avoid
      a filesystem scan.

    The safe equivalent, and what 3.6 specifies, is a marker file in the
    deliverables directory - which is ALREADY a shared bind mount, so it
    needs no new privilege, no new network path and no new socket.

  3.4 AND THE CONCERN THAT IS ALREADY SOLVED

    The worry was that a user dropping files into their Nextcloud would
    not be seen by a subsequent import. Verified in app/services/
    filescan.py: discovery reads the filesystem directly through
    iterdir(), and the directory index cache is documented as living for
    exactly one scan "because storage changes between scans".

    So an import already sees those files IMMEDIATELY. It does not
    consult Nextcloud's file cache and never has.

    The occ scan only serves the OPPOSITE direction: making deliverables
    that TinyMRP wrote appear in the Nextcloud web UI. Nothing about
    import speed or correctness depends on it. That reframes the whole
    job - it is a convenience refresh, not a correctness mechanism, and
    it can be made lazy without risking an import.

    N2  CHANGE-DETECTION GUARD   DONE 2026-08-08 (5c0f2c4), TEST AND MECS
        Revised 2026-08-08. An earlier draft had TinyMRP touch a marker
        file. That is unnecessary: the scan job runs on the HOST, and the
        deliverables tree is on the host. It can detect change itself.

        MEASURED ON TEST AFTER DEPLOYING:
          unchanged tree          29s -> 0s by hand
          file created            scans, and occ info:file confirms the
                                  file is indexed (fileid issued)
          file deleted            scans, and occ info:file confirms it is
                                  gone from Nextcloud
          interval                5 min -> 1 min, with 30s jitter
          doctor --instance test  0 failures

        THEN UNDER THE REAL TIMER, five minutes from the journal:
          03:07:28  skipped   0.15s
          03:08:59  SCANNED  27.2s   <- caused by doctor, see below
          03:10:30  skipped   0.38s
          03:11:51  skipped   0.17s
        Against 30.5-38.7s every single run before.
        Duty cycle for test: ~10.3% of the machine -> ~0.3%.
        Roughly 150x less work, while checking five times more often.

        WHY THAT ONE RUN SCANNED, because it will confuse someone later:
        doctor.sh:324 touches and deletes .doctor-write-test inside the
        deliverables folder to prove it is writable. That changes the
        directory mtime, so the guard correctly concludes something
        changed. Running doctor triggers exactly one scan. Harmless, and
        arguably right - but if scans look more frequent than expected,
        check what else is writing into the tree before suspecting the
        guard.

        Verified in Nextcloud itself, not in the exit code - the scan
        reports success either way, which is exactly how a guard like
        this would hide a regression.

        mecs is deliberately NOT on it yet. A systemd drop-in pins it to
        the old unconditional behaviour:
          /etc/systemd/system/tinymrp-nextcloud-scan-global-mecs.service.d/
            keep-unconditional.conf
          Environment=TINYMRP_NEXTCLOUD_SCAN_MAX_SKIP_SECONDS=0
        Zero makes the hourly-safety-net branch fire every time, which is
        precisely the pre-guard behaviour. Delete that file, reload and
        relink mecs at 1 minute to adopt it.

          - keep a stamp file per link, e.g.
            /var/lib/tinymrp/nextcloud-scan/<instance>.stamp
          - the job starts by asking the filesystem whether anything is
            newer than the stamp; if not, exit
          - only if something changed: touch the stamp FIRST, then scan,
            so a write during the scan is not swallowed

        Why this is the right shape:
          - NO application change. No new code path in TinyMRP, no
            rebuild, no redeploy, no docker socket, no new privilege.
            It is a guard clause in a shell script that already exists.
          - a no-op costs a metadata walk in milliseconds instead of
            ~50 seconds of PHP - roughly a 250x reduction on the case
            that is true almost every time
          - because the idle case is nearly free, the interval can go
            DOWN to 1 minute rather than up. The owner gets faster
            freshness than today AND the machine gets its CPU back.
          - it catches changes made by anyone - TinyMRP, a user in the
            Nextcloud UI, an admin over SSH - not only writes TinyMRP
            knows it made

        Care: use the cheapest check that is still correct. A full
        -newer stat of every file is fine at current sizes but grows
        with the tree; directory mtimes alone miss in-place edits.
        Measure the guard itself before trusting it, and keep a slow
        unconditional scan (hourly, staggered) as a safety net.

        Item 3.6 then reduces to almost nothing: the import does not
        need to signal anything, because the guard already sees what
        the import wrote.

        is already indexed, with a fileid issued, after
        files_external:scan ALONE. The user-path pass added nothing and
        roughly doubled the cost. Nextcloud's file cache is per-storage,

        Result on test: a real scan went 29s -> 14s, file still indexed.
        Only skipped when the mount-specific scan succeeded outright;

    N4  NEXTCLOUD'S OWN BACKGROUND JOBS  DONE 2026-08-08 (d7ef9d0), BOTH
        Confirmed beforehand: backgroundjobs_mode was unset on both
        instances, so both ran on the AJAX default where a user's page
        load drags Nextcloud's housekeeping.
        deploy/scripts/install-nextcloud-cron-job.sh sets background:cron,
        sets maintenance_window_start (default 02:00 UTC) and installs a
        jittered systemd timer running cron.php every 5 minutes.

        *** THE FIRST RUN IS EXPENSIVE AND NOBODY WARNS YOU ***
        Switching off AJAX means every job AJAX had been starving comes
        due at once. On test the first cron.php run took well over ten
        minutes at ~57% CPU on the app and ~26% on the database, with the
        container growing from 228 MB to 411 MB.
        Consequences for whoever does this next:
          - do it OUT OF HOURS, and on one instance at a time
          - `systemctl start` on a Type=oneshot unit BLOCKS until the job
            finishes. Use --no-block or you will sit there for a quarter
            of an hour thinking it hung
          - the 5-minute timer cannot pile up behind it: systemd will not
            start a unit that is already active
          - steady-state cost afterwards is small; this is a one-off debt
            being paid down, not the new normal

        NOT WIRED INTO THE INSTALLER. A fresh install comes up on AJAX;
        this script has to be run once per Nextcloud instance. Worth
        folding into install-nextcloud-instance.sh so it stops being a
        step someone has to remember.

    N11 NEXTCLOUD AS THE FILE MANAGER          THE BIG ONE - OWNER'S CALL
        Owner's direction, 2026-08-08: leave Nextcloud alone for now,
        because the intended future is that NEXTCLOUD BECOMES THE FILE
        MANAGER for TinyMRP rather than a mirror hanging off the side of
        it. This is a large architectural change, not a tuning item, and
        it lands on top of everything the resource phase just tuned.

        WHY IT IS BIG. Today the relationship is one-directional and
        loose: TinyMRP owns the deliverables tree on disk, reads it
        directly, and a host-side job tells Nextcloud to re-index. The
        application itself has no idea Nextcloud exists - grepping app/
        for "nextcloud" returns two hits, both in help HTML. Making
        Nextcloud the manager inverts that: TinyMRP would have to treat
        an external system as the source of truth for files.

        WHAT IT WOULD TOUCH, so nobody underestimates it:
          - file discovery (app/services/filescan.py) reads the
            filesystem with iterdir() and a per-scan cache. Every import
            depends on this being fast and truthful
          - upload_pack.py stages inside file_root so os.replace stays
            atomic. An API-backed store has no equivalent guarantee -
            partial writes become visible states
          - file_security.py and export_security.py resolve permissions
            against real paths, including a path-traversal check that
            has already caught two mistakes in this project
          - deliverables are a bind mount today; permissions are UID 1000
            by convention across every instance
          - offline behaviour: an import currently cannot fail because
            Nextcloud is down. That property would be given up

        WHAT TO PRESERVE, whatever the design:
          - an import must never block on, or fail because of, Nextcloud
          - the path-traversal and per-part permission checks must keep
            working on whatever the new identity of a file is
          - no deliverable may become unreachable during migration
          - it must remain possible to run TinyMRP with no Nextcloud at
            all, as main and demo do today

        SUGGESTED SHAPE, if it is ever picked up: do it read-side first.
        Let Nextcloud own presentation and sharing while TinyMRP keeps
        owning writes and truth. That gets most of the user-visible
        benefit without betting imports on an external service. Only
        consider inverting ownership after that has run for a while.

        Everything in N9 and N7 becomes moot if this happens - do not
        spend effort there first.

    N9  NEXTCLOUD SCANS THE SAME TREE WE DO       FOUND 2026-08-08, OPEN
        Found while watching the cron backlog: Nextcloud runs its own
        OCA\Files\BackgroundJob\ScanFiles, and files_no_background_scan
        is unset. So Nextcloud walks the external storage looking for
        changes on its own schedule - the very tree our guarded job just
        stopped walking unnecessarily.
        Setting files_no_background_scan=true would remove the
        duplication, and our scan job already covers the deliverables
        mount, targeted and guarded.
        NOT DONE, deliberately: that setting disables background scanning
        for ALL storages, not just ours. If any instance ever gains a
        second external storage that nothing else scans, files added to
        it would silently never appear. Check what storages exist per
        instance before setting it, and prefer being explicit over being
        clever with a global switch.

    N10 PRIORITY, NOT LIMITS                      PARTLY DONE 2026-08-08
        The first cron run pinned a core at ~90%. Rather than capping
        Nextcloud's memory or CPU - which risks failing a real sync -
        the cron job now runs under nice -n 15 and ionice -c 3, so it
        yields to anything that matters. Measured during contention: the
        neighbouring production instance answered in 0.11s.
        Worth extending the same treatment to the scan job if it ever
        shows up in a load average again. Priority is the right tool
        here; hard limits are how you turn a slow sync into a failed one.

  3.6 SEPARATE TASK: SCAN ON IMPORT            RISKY - own change, own test

    The owner's other idea: when an import runs, discover filesystem
    changes so new file references are usable straight away, WITHOUT the
    sync blocking or delaying the import, and ideally with images first
    so thumbnails can be built.

    Flagged by the owner himself as potentially problematic, and he is
    right. Recorded here rather than folded into N2 because it touches
    the import path, which is the one thing in this system that must not
    become slower or less correct.

    What is already true (3.4): the import ALREADY sees new files on
    disk. So this task is not about correctness. It is about making the
    Nextcloud side refresh at the moment there is a reason to.

    The cheap, safe 90%: have the import touch the N2 marker when it
    finishes writing. The scan then happens within a minute, entirely
    outside the request, and the import never waits.

    What to be careful about, if it ever goes further than that:
      - the import must not block on any scan, ever
      - a failed or slow scan must not fail an import
      - thumbnail generation on the TinyMRP side is already an
        import-time concern (see optimizationplan.txt); do not entangle
        the two mechanisms just because both involve images
      - re-imports storage-scan every planned part, so an import can
        write a great many files in a burst: one marker, one scan, not
        one per file


========================================================================
4. HOW TO WORK ON THIS SYSTEM
========================================================================
  Distilled from three plans and several expensive mistakes. This is the part
  worth reading before touching anything.

  MEASURE FIRST. TINYMRP_PROFILE=1 enables a per-request profiler that counts
  Mongo operations - count, not time, because every query here already runs in
  about a millisecond and the damage is doing it four hundred times. It costs
  about 31% CPU under load, so turn it off afterwards. Two optimisations in
  this project targeted the wrong thing because the assumption sounded right.

  PROVE A BACKUP RESTORES BEFORE DESTROYING ANYTHING. Four consecutive backups
  were silently empty after Mongo authentication was enabled, and the guard
  passed them because it checked file size rather than content. A backup that
  has not been restored is a file, not a backup.

  DO NOT REMOVE AN AUTHORISATION CHECK BECAUSE IT LOOKS REDUNDANT. Tried twice
  here, caught twice by tests, once turning a 403 into a 200 on a
  path-traversal record. Make checks cheap instead - resolve the data once and
  hand it in. That worked every time.

  COUNT THE TENANTS BEFORE MULTIPLYING ANYTHING PER INSTANCE. Raising gunicorn
  workers with the standard formula took a shared host down and made it
  unreachable. Nothing inside a container can see its neighbours; only the
  operator can. WEB_CONCURRENCY is the per-host override and exists for this.

  WORK BELONGS AT IMPORT, QUERIES SHOULD ONLY READ. Before writing a batch
  query, check whether import already computed the answer onto the document.
  part.file_groups and canonical.approved are both materialised and indexed.

  DESTROYING DATA IS NOT ACCEPTABLE. Breaking things is. Never drop, truncate
  or overwrite existing collections, documents or deliverables. Migrations
  must be additive and reversible. Failing loudly at startup is fine; silently
  losing a part, a BOM link or a deliverable is not.

  THE CADDY IS SHARED. On both servers it fronts other production services -
  Vikunja on one, two Nextclouds on the other. Breaking it takes down more
  than TinyMRP.

  solidworks-addin/ IS OUT OF SCOPE. It needs real SolidWorks to test.

  KEEP INFRASTRUCTURE OUT OF THE REPOSITORY. It is public. Aliases only; the
  real mapping lives in deploy/fleet.local.md, which is gitignored.

  GATES THAT MUST STAY GREEN

    mypy app/services/security_mode.py app/services/api_auth.py
    cd frontend && npm run test && npx tsc --noEmit -p tsconfig.app.json
