========================================================================
OPTIMIZATION PLAN — making TinyMRP fast and cheap again
========================================================================
Opened 2026-08-08. Branch: main.
Supersedes item P1 of posthardeningplan.txt, which is now closed.

WHY THIS EXISTS, in the owner's words:

  "the most important thing in this project - browsing part numbers and their
   trees fluidly - we have ruined with so much security and checking"

That is accurate. Low resource use was an original goal of TinyMRP. The
hardening work traded it away without measuring what it cost, and this plan
buys it back with measurement rather than instinct.

WRITTEN FOR A HANDOVER. Anyone picking this up - human or another AI - should
be able to continue from section 3 without asking questions. Record what you
measure, including the attempts that fail.


========================================================================
1. WHAT IS ALREADY KNOWN — do not re-derive this
========================================================================

  MEASURED ON THE LIVE test INSTANCE (1789 parts, 6.8 GB deliverables):

  a) The server IS idle when idle. Profiling 30 s with no user activity
     captured 16 operations total - about 0.5/sec, all of them the 60-second
     notification poll from one open browser tab.
     *** This disproves the "something is hanging or looping in the
     background" theory. Do not spend time there again. ***

  b) The waste is INSIDE each request. The headline figure of ~22 find/sec was
     an AVERAGE over 937 minutes that included real browsing. Concentrated in
     navigation, it means each page load is enormously amplified.

  c) Individual queries are fine. bom by parent_pn: 1 ms, 3 documents
     examined, 3 returned - properly indexed. The problem is COUNT, not cost.

  d) Authorisation walk, now fixed: _bom_is_fully_authorised took 1801 ms to
     visit 1347 parts across 10 levels, on every flat-BOM request, to answer a
     question that could not have been "no" for an unrestricted user.

  e) Capacity, now fixed: the image hardcoded 2 workers x 4 threads = 8
     concurrent slots for the whole instance, on any hardware. A part page
     fires roughly a dozen requests.

  f) Connection churn: 24,903 connections created against 17 concurrent. Not
     yet explained. Suggests the Mongo pool is not reused across requests.

  g) parts_lazy full breakdown (this is the model for how to measure):
       config=46 filters=0.2 query=71 thumbs=524 review=0 rows=64 total=705ms
     for 25 rows. thumbs was 74% and is now answered from the database.

  ALREADY DONE (before/after where measured):
    - workers sized from nproc: 8 concurrent slots -> 20 and 36 on the two
      servers in use
    - subtree authorisation skipped when the scope filters nothing: -1801 ms
      per flat-BOM request
    - bom_flat: all parts in one query, per-node re-authorisation removed
    - bom_flat thumbnails batched: one storage pass instead of ~65 ms per part
    - thumbnail existence answered from PartFile.thumb_mtime, not the disk
    - parts inventory: 705 ms -> 529 ms, then the database fast path (final
      figure NOT yet measured - see 3a)

  *** THE OWNER NAVIGATES WITH bom_tree. Almost all tuning so far went into
  bom_flat. bom_tree is the hot path and has NEVER been profiled. ***


========================================================================
2. THE TOOL TO BUILD FIRST — a switchable request profiler
========================================================================
  The owner asked for something that can be turned on and off, adds no
  overhead when off, and makes it obvious where resources go. Build this
  BEFORE optimising anything else: every wrong guess so far came from not
  having it.

  DESIGN, and the constraints that shape it:

  Enabled by TINYMRP_PROFILE=1 and nothing else. When unset, no listener is
  registered, no timer is started, and no branch runs inside a request. Zero
  cost is the requirement, not a goal - a profiler that slows production is
  one nobody dares enable.

  WHAT IT MUST REPORT, per request:
    - total wall time
    - NUMBER of Mongo operations, split by collection and by shape
    - the slowest single operation
    - number of filesystem stats (the thumbnail path was invisible until
      someone counted them)

  Query COUNT matters more than query time here. Every individual query
  already runs in about a millisecond; the damage is doing it four hundred
  times. A profiler that only reports slow queries will show nothing.

  HOW TO HOOK IT:
    pymongo exposes monitoring.CommandListener with started/succeeded/failed.
    Register it ONCE at startup, only when the flag is set - pymongo
    registration is process-global and cannot be undone, which is exactly why
    it must be conditional rather than toggled per request.
    Accumulate into flask.g per request, emit one log line in an after_request
    handler, and log at INFO under a dedicated logger name (tinymrp.profile)
    so it can be filtered without turning on DEBUG for everything.

  Follow the shape of the existing tinymrp.parts_lazy timing line. It is the
  reason the inventory problem was diagnosed correctly rather than guessed at,
  and it is already proven in production.

  A GOTCHA THAT WILL COST AN HOUR: driving the app with Flask's test client
  does not authenticate under strict mode - setting _user_id in the session is
  not enough, and every request returns 401 with zero queries. Either exercise
  it through a real logged-in browser session while the profiler is on, or
  profile in an app context calling the view functions directly.


========================================================================
2b. FIRST PROFILER RESULTS — 2026-08-08, real browsing on test
========================================================================
  The owner's suspicion, in their words, turned out to be exactly right:

    "when we load data in the web client it should be only what the user sees.
     It makes no sense to analyse a whole assembly tree and read the data if
     we are only going to show the first level."

  Measured, per request, with TINYMRP_PROFILE=1:

    GET /api/docpacks/options?depth=full   4203 ms   589 mongo ops
        parts=262  bom=130  part_files=130  part_drawing_markups=65
    GET /api/bom_flat                      1948 ms   372 mongo ops
        part_files=193  bom=130  parts=43
    GET /api/docpacks/options (another)    6732 ms   341 mongo ops
    GET /api/bom_tree  (ONE level)         1001 ms    64 mongo ops
        part_files=33  parts=23  app_settings=2  users=1
    GET /api/part_detail                   2106 ms    52 mongo ops

  WHAT THIS SAYS:

  a) *** /api/docpacks/options?depth=full is the single worst offender and it
     fires on EVERY part detail page load. 589 queries and 4.2 seconds to walk
     an entire subtree, in order to populate a dropdown of options. The user
     has not asked for a docpack at that point and may never do so. This is
     the clearest example of reading everything to show a little. ***
     Fix: do not compute full-depth options until the user opens that control,
     or compute them from counts rather than by walking every part.

  b) bom_tree costs 64 queries to expand ONE level. With roughly twenty
     children that is about three queries per child - a textbook N+1. The
     level itself is already batched; what is not batched is what happens per
     child inside _node.

  c) app_settings is read 2x and users 1x on EVERY request. Small individually,
     but it is fixed overhead paid by every call including cheap ones.

  d) part_files dominates almost every request (193, 130, 33, 20...). Whatever
     reads it is doing so per part rather than per request.

  e) Query TIME is not the problem: the slowest single operation in the whole
     sample was 212 ms and most are under 20 ms. Confirms the profiler was
     built to count rather than to time.

  PRIORITY ORDER derived from this, replacing the guesses in section 3:
    1. docpacks/options on page load - biggest win, and arguably it should not
       run at all until requested
    2. part_files access pattern - it is in every hot path
    3. bom_tree per-child work inside _node
    4. app_settings and users per request - cache for the request lifetime

2c. THE GOVERNING PRINCIPLE — stated by the owner, and it is correct
========================================================================

  "It is at import time that everything gets filtered and indexed, so that
   queries do no post-processing and only read the database. If something
   changes after the import, that is what the rescan functions are for."

  Applies to file scanning, properties, aliases, approval and thumbnails.
  AUDITED 2026-08-08. The architecture already implements this; the violations
  were in QUERY paths that ignored it.

    VERIFIED COMPLIANT
      thumbs.py, bom_tree.py, parts.py   zero filesystem calls
      file_security.py                   6 calls, only when SERVING a file the
                                         browser actually requested
      generate_thumbs_for_parts          called only from the explicit
                                         POST /parts/<pn>/refresh_files
      canonical.approved                 materialised AND indexed
      part.file_groups, has_pdf/step/... written at import by
                                         sync_part_materialized_fields

    VIOLATION FOUND AND FIXED
      _coverage_groups recomputed file coverage from PartFile on EVERY node -
      3852 part_files queries in one flat-BOM request - when part.file_groups
      already held exactly that answer, denormalised at import. The data was in
      the database; the query path was not reading it.

  *** THE TEST TO APPLY TO ANY REMAINING HOT PATH: if a value can be computed
  at import, it must be READ, not recomputed. Look for the answer already
  sitting on the document before writing a batch query for it. ***

3. THE WORK, IN ORDER
========================================================================

  DONE, with measurements from the live test instance.

  P-1. Request profiler                                DONE
       TINYMRP_PROFILE=1, counts Mongo ops per request, one line under
       tinymrp.profile, zero cost when unset.
       Two gotchas that cost real time: the listener MUST subclass
       monitoring.CommandListener or registration fails into your own error
       handler, and it MUST be registered before the Mongo client is created
       or it counts nothing forever while looking perfectly healthy.

  P-2. Worker capacity                                 DONE
       Was a fixed 2 workers x 4 threads = 8 concurrent slots on any hardware.
       Now (2 x nproc) + 1, floored 4, capped 12, via WEB_CONCURRENCY from the
       entrypoint. 8 slots -> 20 and 36 on the two servers in use.
       This alone explains "hangs, then recovers": a page fires about a dozen
       requests, so browsing saturated the pool until things timed out at 120s.

  P-3. Subtree authorisation walk                      DONE
       1801 ms visiting 1347 parts on every flat-BOM request, to answer a
       question that could not be "no" for an unrestricted user. Skipped via
       parts_scope_is_unrestricted(). Tests assert when it must NOT fire.

  P-4. Doc-pack options on page load                   DONE
       4203 ms and 589 queries on EVERY part page view, walking a whole subtree
       to fill a dropdown most visits never open. Now fetched only when the Doc
       Packs tab is opened; changing part clears and re-arms it.
       The subtree authorisation was DEFERRED, not removed: a doc pack contains
       its children's documents, so dropping that check would turn a slow page
       into a data leak.

  P-5. BOM level part lookup                           DONE
       _node issued one Part query per child; now one query per level.
       parts=426 for a 1347-part subtree, down from one per part.

  P-6. File coverage                                   DONE
       Read from part.file_groups instead of recomputing from PartFile per
       node. See 2c.

  STILL OPEN, in priority order.

  P-7. bom queried once per node                       DEPRIORITISED
       Was next. After P-12 almost nobody runs bom_flat, so repairing the
       algorithm of something no longer called is effort in the wrong place.
       Kept because it still bites whoever presses Flat on a big assembly.
       Measured: bom=4430 in one flat-BOM request on J200684.
       _child_links fetches one parent's children per call and the traversal
       calls it per node. Batching means restructuring the descent to work
       LEVEL BY LEVEL rather than depth-first, collecting each level's children
       in one query. A real change to the traversal, not a patch, which is why
       it was not started at the tail of a session.
       bom_tree already does this correctly for the level it renders; it is the
       flat and subtree walks that do not.

  P-8. app_settings re-read                            DONE
       Was 2x per request and 593 times in one docpacks/build. Now memoised
       per request - deliberately not globally, so an administrator's change
       takes effect on the next request rather than after a restart. Nothing
       is memoised outside a request context, so CLI and import read fresh.

  P-12. Flat BOM loaded on every page view             DONE
       8717 queries and 55 seconds on J200684, on EVERY part view, while the
       user was looking at the tree. Now fetched only when the Flat button is
       pressed; changing part drops the previous rows.
       Together with P-4 this is the headline finding of the whole exercise:
       the page was not slow because the backend is slow. It asked for three
       expensive things on every view and the user had requested one.

  P-9. Connection churn                                NOT STARTED
       24,903 connections created against 17 concurrent. Check whether
       MongoEngine reconnects per request, and whether the pool size suits the
       new worker count - each worker holds its own pool, so raising workers
       multiplies connections.

  P-10. Requests per page                              NOT STARTED
       A part page fires roughly a dozen API calls. Count them from the access
       log first; fewer round trips beats faster ones over a real network.

  P-11. Notification poll                              LOW PRIORITY
       60s interval per page, four queries each, restarted on every full page
       navigation. About 7 requests/minute per open tab. Real but small.

  P-13. Idle CPU and RAM on the host                   NOT STARTED
       Owner reports the VPS control panel showing load averaging above 40%
       and RAM at 100% while idle. Several services share that box, so some of
       it is not TinyMRP - but it should not sit at the limit.
       WHERE TO LOOK, and note the first item cuts both ways:
         - gunicorn workers were just raised from 2 to (2 x cores) + 1. Each
           worker is a full Python process holding its own Mongo pool, so this
           TRADED memory for concurrency. If RAM is the binding constraint,
           lower WEB_CONCURRENCY on that instance and measure - the setting
           exists precisely so it can be tuned per host.
         - the owner's hypothesis: comments and notifications forcing
           continuous checking, or sweeping all users. Worth testing directly.
           Known so far: the notification poll is 60s per open tab and issues
           four queries (users, roles, user_notifications x2). Small per tab,
           but it is per TAB and it restarts on every full page navigation.
         - measure per-container rather than per-host first:
           docker stats --no-stream. An earlier reading showed the app at
           173 MiB and Mongo at 298 MiB, which is modest - so if the host is
           at 100%, look at what else is on it before blaming TinyMRP.
         - Mongo's WiredTiger cache defaults to half of RAM. On a shared box
           that alone can look like "RAM at 100%". Check whether a cache size
           is configured; if not, that is the likely explanation and it is one
           compose setting.

  P-14. Instance updates got slow to start             NOT STARTED
       Owner reports containers taking much longer to come up after
       update-instance.sh than they used to.
       LIKELY CAUSE, and it is self-inflicted: the app HEALTHCHECK was moved
       from /api/health to /api/ready, and start-period was raised 25s -> 60s.
       Readiness pings Mongo and checks storage, so "healthy" now genuinely
       waits for dependencies instead of reporting the process exists. Some of
       the delay is therefore correct and wanted.
       What to check before changing anything: whether the container is
       actually READY earlier than it is reported healthy - if so, the
       healthcheck interval and retries are the cost, not the app. Also
       whether more gunicorn workers simply take longer to fork and import.

  METHOD - unchanged, and it has earned its place:
    1. Measure before changing.
    2. Count queries per request; an N+1 hides as a fast query repeated.
    3. Fix by batching, not caching.
    4. Better still, read what import already computed (see 2c).
    5. Delete checks that cannot fail rather than making them faster.
    6. Record BOTH numbers in the commit message.

4. EXIT CRITERIA
========================================================================
  - Browsing a large assembly on the test instance stays responsive: no hang,
    no recovery period, verified against J200684 specifically.
  - Mongo CPU near zero with nobody using the system. Currently true at idle;
    keep it true.
  - Query count per page load recorded and justified. "It is fast enough" is
    not a number.
  - Before and after figures recorded here for every change.


========================================================================
5. STANDING CONSTRAINTS
========================================================================
  Speed must not be bought with security. The authorisation shortcut added so
  far is safe for one specific reason - the check it skips could not have
  returned "no" - and its tests assert when it must NOT fire. Any further
  shortcut needs the same argument in writing.

  Real companies run this. Breaking things is acceptable; destroying data is
  not. The mecs instance is out of scope entirely.

  Infrastructure is referred to by alias. Real addresses live in
  deploy/fleet.local.md, which is gitignored. This repository is public.

  Gates that must stay green:
    pytest | ruff check . | bandit -r app -ll
    mypy app/services/security_mode.py app/services/api_auth.py
    cd frontend && npm run test && npx tsc --noEmit -p tsconfig.app.json
