4. WHAT IS LEFT — engineering

  E2. Silent exception handlers — 162 of 184 remain
      *** THE TRIAGE FOUND A REAL SECURITY BUG, not just a debuggability one.
      Bulk user deletion FAILED OPEN. The guard protecting administrators
      swallowed its own exception and fell through to u.delete(), so a broken
      role reference or a momentary database error deleted the very
      administrator it exists to protect - and the same for the guard stopping
      you deleting your own account. Deletion is irreversible, so both now skip
      the user and say so. Pinned by a test that also fails if any bare pass is
      reintroduced anywhere in that loop. ***
      Also converted on this pass:
        runtime_secrets - a failed chmod 0600 on a SECRETS file was silent, so
          a world-readable secrets file would never have been noticed
        extra_files - the ROLLBACK itself failed silently, leaving the database
          holding a record the filesystem no longer matched, with nothing
          saying which record to reconcile
        a failed user deletion is now counted and surfaced: references are
          cleaned up BEFORE the delete, so a failure leaves damage behind

  E2-old. Earlier pass — 170 of 184 remained
      Triage, not a rewrite: suppressing a thumbnail render inside a loop is
      legitimate; suppressing a write is how a defect becomes undebuggable.
      DONE: the 14 that can hide data or security loss - the import journal
      (which was LYING about the stage reached when a write failed), file
      deletion, an authorization denial with no audit trail, public share
      creation, and five review notifications.
      LEFT ALONE on purpose: audit.log_action's own nested guards. An audit
      failure must never break the operation it is recording.
      REMAINING, concentrated in docpacks.py (36), admin.py (20), parts.py
      (20) and __init__.py (19). Mostly best-effort UI and rendering paths,

4b. BUGS REPORTED FROM THE LIVE TEST INSTANCE
========================================================================

  B1. BOM child links sent the parent's revision — FIXED 2026-08-07
      Reported as "part details ok but buggy with the links". The address bar
      was correct and every request still failed.
      React does not unmount the detail page when only a route param changes,
      so the previously loaded part stayed in state and supplied ITS revision
      until the new fetch landed. Clicking a child whose revision is blank,
      from a parent at revision "1", sent part_detail, files_overview, shares,
      images and docpack options all out with rev=1 - a page of 404s.
      A loaded part now supplies the revision only while it IS the part in the
      URL. Extracted to src/lib/partIdentity.ts with 5 tests, matched
      case-insensitively because the backend matches part numbers that way.
      Very likely the same root cause as the older report that a child's BOM
      stayed visible while its parent loaded.

  B2. bom_flat stormed the storage — FIXED 2026-08-07
      Clicking a large child timed out. bom_flat was the unoptimised sibling of
      bom_tree: when bom_tree went from 35s to 77ms it gained batched lookups,
      and bom_flat kept calling preview_png_urls_for once per unique part at
      ~65 ms each. Now one link walk collects every distinct part and all
      thumbnails resolve in a single batch.

  B3. Parts inventory latency — THREE PASSES, THE LAST ONE UNMEASURED
      Measured with the endpoint's own instrumentation, never guessed.

        BEFORE   config=46 filters=0.2 query=71 thumbs=524 rows=64  total=705ms
        PASS 1   thumbs=370-476                                     total=529-678ms
        PASS 3   deployed to test, NOT YET TIMED

      RULED OUT, so nobody re-investigates: parts_lazy already paginates
      (25 rows), preview_png_urls_map already batches at the DATABASE level,
      the created_at sort is indexed, and /api/field-config is 55 KB of SIZE
      not latency (its computation is the config=~46 ms bucket - real, but not
      the problem).

      Pass 1 - a request-scoped directory listing cache. Only ~25%, and the
      reason is worth keeping: I assumed each part's files sat in their own
      directory. The storage is FLAT - 33 directories for 10990 files, with
      thumbs/png holding 2457 alone - so the one scandir reads 2457 entries and
      eats most of the saving.

      Pass 2 - _validate_candidate re-resolved the storage ROOT for every
      candidate, the same path dozens of times per request. Memoised.

      Pass 3, the real fix - stop asking the filesystem at all.
      thumb_mtime already existed on PartFile and is written the moment a
      thumbnail is generated, so availability is answered from the record.
      Records without it still fall back to disk, so older data is unchanged.
      SAFE FOR TWO REASONS, both stated because "trust the DB" is normally the
      wrong instinct in file_security.py:
        - a wrong YES cannot grant access. It only decides which URL goes on a
          row; serving still resolves with must_exist=True, so a deleted file
          is a 404, never a bypass.
        - a 404 is not a broken page. ThumbImg walks its candidates and settles
          on the branding logo, so a stale record degrades to a placeholder.

      NEXT: load /ui/parts on test with LOG_LEVEL=DEBUG and compare. If thumbs
      is still the dominant bucket, the remaining cost is Path.resolve() per
      candidate and the option not yet tried is resolving relative to an
      already-resolved root.

      CONSTRAINT for whoever continues: this is file_security.py, the
      path-traversal guard. Speed must never come from weakening containment.
      tests/test_file_security_listing_cache.py pins that boundary - a file
      that genuinely exists outside the root is still refused, traversal is
      still refused, and the cache is proved off outside a request context.

4c. B4 — bom_flat is still O(N) DATABASE queries  *** CAUSES 502s ***
========================================================================
  Reported: a part detail returns 502, and the flat BOM "takes forever".
  Both are the same thing. gunicorn runs --timeout 120 with 2 workers, so a
  request that outlives that is killed and the proxy answers 502.

  MEASURED on the reported part: 7 levels deep, 183 link rows, 163 DISTINCT
  parts.

  The thumbnail batching (B2) fixed the FILESYSTEM side. The database side is
  untouched: row_for() runs per distinct part and each one does
    - scoped_parts.filter(...).first()      one query per part
    - _coverage_groups(pn, rev)             another lookup per part
    - resolve_part_field_values / filter_response_fields
  plus _bom_is_fully_authorised walking the whole subtree first, and
  authorised_part_pairs called again per node during the descent.

  So ~163 parts becomes several hundred round trips. That is the remaining
  cost, and it grows with assembly size - which is why small instances never
  showed it.

  THE FIX, same shape as every other one here: collect the distinct pairs
  first (the walk already exists - _flat_subtree_pairs), then resolve parts,
  coverage and field values in BATCHES, and drop the redundant per-node
  authorisation now that the subtree is proved once up front.
  NOT started: this is a real refactor of bom_flat's traversal, not a patch,
  and it deserves a full pass rather than the tail of one.

  INTERIM RELIEF if it bites before then: raising gunicorn --timeout turns a
  502 into a slow page, which is less alarming but not a fix.

  Reported: clicking where-used on a parent lands on /ui/part/<pn>?rev= and

  Check the server-side /ui/part/<pn> handler first, and while there, decide
  whether those two <a href> links should be <Link> like their neighbours - a
  full reload of a heavy SPA is also why those clicks feel slow.

6. THINGS THAT WILL BITE YOU
========================================================================
  Learned the expensive way. Read before touching deployment.

  update-instance.sh does NOT rebuild the image.
      Without --image it regenerates the compose file only. That applied a new
      /api/ready healthcheck against an image predating the endpoint: eleven
      404s, never healthy, automatic rollback. Build first, pass --image.
      A compose healthcheck applies the moment the file is regenerated; the
      image changes only when you ask for it.

  update-instance.sh never writes the instance .env, and uses --no-deps.
      Both deliberate. Rollback restores the compose file and container, so an
      env edit would survive the rollback meant to undo it; and --no-deps
      means it recreates ONLY the app, so a new sidecar (redis) never starts.
      Anything touching .env or sidecars needs its own attended script.

  Mongo only enables auth while initialising an EMPTY data directory.
      Setting MONGO_INITDB_ROOT_* against an existing volume does nothing, and
      says nothing. That is why enable-mongo-auth.sh exists.

  cap_drop: ALL removes CAP_CHOWN.
      The redis entrypoint chowns /data when it starts as root, so the
      container crash-looped on "chown: Operation not permitted". Fixed with
      user: redis. The contract tests passed throughout - they assert the
      service is DECLARED correctly. Only starting it on a real box found it.

  The installer's DNS wait had no timeout when there is no TTY.
      It prompted with a terminal and slept forever without one, so an
      unattended install hung instead of failing. Now bounded
      (DNS_WAIT_MAX_ATTEMPTS). A hang is worse than an error.

  Flask-Limiter: the problem was ordering, not decoration.
      init_rate_limiting runs hundreds of lines before the blueprints are
      registered, so an endpoint lookup there finds nothing and skips in
      silence. apply_expensive_limits() is called after the routes exist.

  vite build does NOT type-check.
      An extraction once shipped a page that could not load. The
      noUndefinedIdentifiers test runs tsc --noEmit and fails on TS2304/TS2552
      only. Run it after any extraction.

  Part numbers are matched case-insensitively throughout. Do not "optimise"
  that away - an $in of compiled case-insensitive regexes is deliberate.

7. STANDING RULES
========================================================================
  DEPLOYMENT REALITY (owner)
    Real companies run TinyMRP now. Breaking things is acceptable. DESTROYING
    DATA IS NOT.
      - never drop, truncate or overwrite existing collections or documents
      - never delete or rewrite files under the deliverables root
      - migrations must be additive and reversible
      - failing loudly at startup is FINE; silently losing a part, a BOM link
        or a deliverable is NOT

  OUT OF SCOPE
    solidworks-addin/ - needs real SolidWorks to test; the owner handles it.
    The mecs instance - the owner said do not touch it.

  PROTECTED PATH
    The guided Caddy deployment must keep working, and on BOTH servers that
    Caddy is SHARED with other production sites. Breaking it takes down more
    than TinyMRP. Anything touching auth, files, containers, health,
    networking, env or deployment must re-check the Caddy contract tests.

  KEEP THE REPOSITORY CLEAN OF INFRASTRUCTURE
    This repo is public. Never commit IP addresses, real customer domains or
    server hostnames. Use aliases and keep the mapping in
    deploy/fleet.local.md, which is gitignored.

  REDUCE FAT PROGRESSIVELY
    Every pass leaves the code leaner: fewer one-use helpers, fewer variables
    that restate the next line, no comment repeating what the code says. Cut
    restatement - keep the reasoning that stops a bug being reintroduced.

  VERIFICATION DISCIPLINE — the rule that produced everything above
    Do not claim a gate is closed because tests pass. Prove the mechanism:
      - the least-privilege Mongo user was verified by trying to read admin
        and being refused
      - the coverage threshold was verified by deleting a test and watching
        CI fail
      - the undefined-identifier guard was verified by removing an import
      - the rate limit was verified by a real 429, after an earlier attempt
        that looked like working code and enforced nothing
      - the backup was verified by restoring it and counting every document
    If a change cannot be proven to work, WITHDRAW it and write down why.
    Something that looks like protection but is not is worse than nothing.

  GATES THAT MUST STAY GREEN
    pytest | ruff check . | bandit -r app -ll
    mypy app/services/security_mode.py app/services/api_auth.py
    cd frontend && npm run test && npx tsc --noEmit -p tsconfig.app.json
