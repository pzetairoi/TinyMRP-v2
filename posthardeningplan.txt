2. WHAT IS LEFT — split by who can actually do it

------------------------------------------------------------------------
2A. OWNER ONLY — engineering cannot close these
------------------------------------------------------------------------

  O1. CSP browser check                         ~30 min      UNBLOCKS SEC-CSP-01
      All 34 inline handlers are delegated, all 18 inline scripts carry a
      nonce, style-src is decoupled. Only a human with a browser can confirm.
        1. Start with TINYMRP_CSP_REPORT_ONLY_STRICT=true
        2. Exercise the admin UI — jobs, orders, fields, roles, add-in
        3. Watch the console for CSP violations
        4. If clean, set TINYMRP_CSP_ALLOW_INLINE=false and repeat
      This is the highest value-per-minute action available to anyone.

  O2. Migrate existing Mongo instances to authentication
      Mongo only creates users on the FIRST boot of an EMPTY data directory,
      so this cannot be automated onto a running instance. Needs a maintenance
      window per instance: enable auth, create the app user, update MONGO_URI.
      Data must not be destroyed — see the deployment-reality rules.

  O3. Execute one real guided VPS install
      The Caddy/VPS path has contract tests and a local isolated stack behind
      it, but NO live install has ever been run. Until it has, "it deploys" is
      an assumption.

  O4. Decide the product position                             COMM-SCOPE-01
      Track A (engineering BOM/document control — what exists) or Track B
      (full MRP — a separate roadmap). Marketing claims must match code.

  O5. Commercial/legal package                                COMM-LEGAL-01
      EULA, privacy policy + DPA, retention/deletion, support and SLA,
      vulnerability-disclosure contact, third-party notices, accessibility
      statement. Needs counsel, not engineering.

  O6. Trivy gate — AUDIT FINDING WAS WRONG, decision still open
      The gate DOES block. `continue-on-error: true` exists only so the SBOM
      and evidence upload run first; "Enforce image vulnerability gate" then
      fails the job. Effective policy today: a FIXABLE HIGH or CRITICAL blocks
      a release (ignore-unfixed: true).
      The owner answered "block only CRITICAL" on the wrong premise, which
      would LOOSEN the gate rather than tighten it. Left unchanged pending a
      decision made with the correct information.

  O7. Give existing instances shared rate limiting
      New instances get Redis from E4. Existing ones keep memory:// until
      migrated by hand, because the update path is deliberately app-only and
      rollback-safe (see E4). Per instance: add RATE_LIMIT_STORAGE_URI to its
      .env and bring the full stack up once so Redis starts.
      Low urgency: the failure mode is a limit that is looser than configured,
      not an outage.

2B. ENGINEERING — ordered by value per unit of risk
------------------------------------------------------------------------

  E1. Error boundary + 404 route            DONE 2026-08-07 (97792a8)
      RouteError on the root route catches render errors for every page;
      NotFoundPage replaced a catch-all that rendered PartsPage — a dead link
      used to look like a successful navigation, so it was never reported.
      Verified the tests detect ABSENCE of the mechanism: removing
      errorElement fails the 3 boundary tests and leaves the 2 not-found ones
      passing. 309 frontend tests, tsc guard clean, bundle rebuilt (it is
      tracked and ships, so a fix that skips the build reaches nobody).

  E2. Triage the 182 `except Exception: pass`     MEDIUM       Phase 8
      Not a blanket rewrite. Classify each: legitimate suppression (best-effort
      loops, optional probes) stays and gets a one-line why; anything on a
      write, auth, import or file-commit path must log at minimum.
      Exit: no silent suppression on a path that can lose or corrupt data.

  E3. Wire /api/ready into orchestration        DONE 2026-08-07
      Every container healthcheck now asks readiness instead of liveness:
      docker/app/Dockerfile (baked into the image, so it applies however the
      container is launched), both compose files, and the per-instance
      renderer. HEALTHCHECK start-period raised 25s -> 60s because readiness
      pings Mongo, which is still warming while the app boots.
      A contract test asserts none of the four still points at /api/health.
      CONSEQUENCE, deliberate and worth knowing: "healthy" is now a real
      claim, so an instance whose Mongo is unreachable, whose deliverables
      volume is unmounted, or which has under 512 MB free will FAIL an update
      and roll back. That is correct - do not deploy onto a broken instance -
      but it means a degraded instance must be fixed before it can be updated.
      READINESS_MIN_FREE_DISK_MB=0 disables the disk check if it ever blocks
      an emergency fix.
      NOT done here: the deploy scripts' own curl checks (doctor.sh,
      install-server.sh, update-instance.sh) still probe /api/health directly.
      They gate on container health anyway, so they inherit readiness; adding
      a readiness-detail report to doctor.sh is a nice-to-have, not a gap.

  E4. Redis in the guided per-instance compose   DONE 2026-08-07
      The rendered per-instance compose now ships Redis (private network only,
      no ports, persistence off, /data on tmpfs) and create-instance.sh writes
      RATE_LIMIT_STORAGE_URI into the instance .env. NEW instances only.
      *** Retrofitting an EXISTING instance from update-instance.sh is wrong,
      and the contract test now says so. Two invariants block it:
        1. update-instance.sh never writes the instance .env - rollback
           restores the compose and container, so an env edit would survive
           the rollback that was meant to undo it.
        2. it recreates the app with --no-deps, so an update never starts the
           Redis container. Writing the URI there would point a live instance
           at a host that does not exist.
      I tried exactly that and the existing contract test caught it. Migrating
      an existing instance is an OWNER action - see O7. ***

  E5. Per-endpoint rate limits                  DONE 2026-08-07
      *** The recorded reason for the earlier withdrawal was WRONG, and the
      real one is more useful. It was not that Flask-Limiter records limits at
      decoration time. It was ORDERING: init_rate_limiting runs at
      app/__init__.py:463 and the blueprints register at 847+, so
      app.view_functions was empty for all six routes and the loop skipped
      every one of them in silence. The endpoint names were correct all along;
      they were asked for too early. ***
      Fixed by splitting out apply_expensive_limits(app), called after the
      blueprints exist. A missing endpoint now logs a warning instead of
      vanishing.
      Budgets (owner: generous, since these are authenticated users doing real
      work and breaking an import session is worse than the abuse a tight
      limit prevents): upload-pack and exports 60/hour, docpacks 30/hour.
      RATE_LIMIT_EXPENSIVE overrides them all at once.
      Keyed by USER, not by address: a company reaches the server through one
      NAT, so an address-keyed budget would be split across the whole office.
      Falls back to the address for the unauthenticated public-share route.
      VERIFIED by a real 429, and verified the test detects the absence of the
      wiring - the old name-resolution test never could, because it inspects
      the finished app, by which time every route is present.

  E6. Page-level tests for the remaining 5 pages  MEDIUM       QA-FE-01
      PartsPage, PartDetailPage, UploadPackPage, AdminFieldsPage,
      AdminAddinPage. Their extracted helpers are covered; the pages are not.
      Add each to coverage.include as it gains real tests — do NOT lower the
      existing thresholds.

  E7. Backup integrity                            MEDIUM       Phase 5
      Checksums, encryption, an off-host copy, and — most important — one
      rehearsed restore. A backup nobody has restored is not a backup.
      Exit: a documented restore drill succeeds from an off-host copy.

  E8. Accessibility baseline                      MEDIUM       Phase 6
      Skip link and stable main target, prefers-reduced-motion in our own CSS,
      live regions for async success/error, keyboard-only pass, focus
      management in modals, accessible names on icon-only controls.
      Labelling is already largely in place (63 htmlFor, 48 aria-label).

  E9. Optimistic concurrency on part edits        MEDIUM       Phase 8
      Two users editing the same part today: last write wins, silently.
      part_drawing_markup.py already has the pattern to copy.
      Must be additive — a new field, never a mutation of existing documents.

  E10. Playwright + axe                           LARGE        QA-FE-01
      Needs CI to boot the app plus Mongo. Also the only way to test the 3D
      viewer and canvas markup, which jsdom cannot run.
      Deliberately last: it is the biggest step and the least certain.

  DELIBERATELY NOT DOING (and why)
    - Mongo transactions for imports. Needs a replica set. The journal is the
      designed "otherwise" branch and it works.
    - Repo-wide Black reformat. 162 files of churn would bury every real diff.
    - UP006/UP045 annotation rewrites (~1100 sites) and SIM105 (103 sites).
      Enormous churn, no runtime benefit, on code running in production.
    - Admin UI over the import journal. The data is reachable over the API,
      which was the blocking part. A page is polish.
    - Breaking up docpacks.py (3336 lines) et al. Real debt, but high-risk
      surgery with no test safety net underneath it yet. Wants E6 first.

4. STANDING RULES — carried over, still binding
========================================================================
  DEPLOYMENT REALITY (owner, 2026-08-04)
    Real companies run TinyMRP now. The owner has root on those machines and
    will absorb breakage and report the error.
    BREAKING THINGS IS ACCEPTABLE. DESTROYING DATA IS NOT.
      - Never drop, truncate or overwrite existing collections or documents
      - Never delete or rewrite files under the deliverables root
      - Migrations must be additive and reversible
      - Failing loudly at startup is FINE. Silently losing a part, a BOM link
        or a deliverable is NOT.

  OUT OF SCOPE
    solidworks-addin/ — needs real SolidWorks to test; the owner handles it.

  PROTECTED PATH
    The guided Ubuntu/VPS deployment using Caddy must keep working. Anything
    touching auth, files, containers, health, networking, env or deployment
    must re-check the Caddy contract tests.

  REDUCE FAT PROGRESSIVELY (owner, 2026-08-05)
    Every pass leaves the code leaner: fewer one-use helpers, fewer variables
    that restate the next line, no comment repeating what the code says.
    Cut restatement — keep the reasoning that stops a bug being reintroduced.

  VERIFICATION DISCIPLINE — the rule that produced this file
    Do not claim a gate is closed because tests pass. Prove the mechanism does
    what it claims: the least-privilege Mongo user was verified by trying to
    read `admin` and create a user and being refused; the coverage threshold
    was verified by deleting a test file and watching CI fail; the undefined-
    identifier guard was verified by removing an import.
    If a change cannot be proven to work, WITHDRAW it and write down why.
    Shipping something that looks like protection but is not is worse than
    shipping nothing — see the withdrawn rate-limit attempt.

  Gates that must stay green:

    mypy app/services/security_mode.py app/services/api_auth.py
    cd frontend && npm run test && npx tsc --noEmit -p tsconfig.app.json
