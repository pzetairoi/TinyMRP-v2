2D. RUN THIS YOURSELF - the guided install needs a terminal
========================================================================
The install cannot be driven from this assistant: without a TTY the script
degrades to unattended mode, which now fails cleanly instead of hanging but
still cannot show you the generated admin password or let you type one.

Run it in your own terminal, where it is interactive:

  ssh ubuntu@SERVER-A
  cd /opt/TinyMRP-v2 && sudo git pull

  # Option A - after repointing test.tinymrp.com at SERVER-A.
  # Validates the FULL path including a real Let's Encrypt certificate.
  sudo ./deploy/scripts/create-instance.sh test test.tinymrp.com       --admin-email admin@tinymrp.com

  # Option B - without touching DNS. Validates everything except real
  # certificate issuance, and burns no Let's Encrypt quota.
  sudo ./deploy/scripts/create-instance.sh test test.tinymrp.com       --admin-email admin@tinymrp.com --skip-dns-check       --local-mode internal-tls

Add --admin-password '<your choice>' to set it yourself; omit it and the
script generates one and PRINTS it at the end - that is the only time it is
shown, so copy it then.

What to watch for, since this is the first guided install ever run:
  - the Caddy route installs, validates and reloads WITHOUT disturbing
    tinymrp.com, cloud.tinymrp.com or vikunja.tinymrp.com on the same proxy
  - the app reaches healthy - it must satisfy /api/ready now, not /api/health
  - a redis container appears beside app and mongo (new in this branch)
  - the instance .env contains MONGO_APP_USER and an authSource in MONGO_URI

If anything fails, nothing is left half-built that I cannot inspect
afterwards - and `main` is backed up, with the restore already proven.

  DEPLOYMENT REALITY (owner, 2026-08-04)
    Real companies run TinyMRP now. The owner has root on those machines and
    will absorb breakage and report the error.
    BREAKING THINGS IS ACCEPTABLE. DESTROYING DATA IS NOT.
      - Never drop, truncate or overwrite existing collections or documents
      - Never delete or rewrite files under the deliverables root
      - Migrations must be additive and reversible
      - Failing loudly at startup is FINE. Silently losing a part, a BOM link
        or a deliverable is NOT.

  OUT OF SCOPE
    solidworks-addin/ — needs real SolidWorks to test; the owner handles it.

  PROTECTED PATH
    The guided Ubuntu/VPS deployment using Caddy must keep working. Anything
    touching auth, files, containers, health, networking, env or deployment
    must re-check the Caddy contract tests.

  REDUCE FAT PROGRESSIVELY (owner, 2026-08-05)
    Every pass leaves the code leaner: fewer one-use helpers, fewer variables
    that restate the next line, no comment repeating what the code says.
    Cut restatement — keep the reasoning that stops a bug being reintroduced.

  VERIFICATION DISCIPLINE — the rule that produced this file
    Do not claim a gate is closed because tests pass. Prove the mechanism does
    what it claims: the least-privilege Mongo user was verified by trying to
    read `admin` and create a user and being refused; the coverage threshold
    was verified by deleting a test file and watching CI fail; the undefined-
    identifier guard was verified by removing an import.
    If a change cannot be proven to work, WITHDRAW it and write down why.
    Shipping something that looks like protection but is not is worse than
    shipping nothing — see the withdrawn rate-limit attempt.
