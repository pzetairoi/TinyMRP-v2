1. HOW TO WORK FROM HERE
========================================================================

  KEEP 1.0 BORING.
    Small commits, one purpose each. Do not mix auth cleanup, RBAC migration,
    frontend typing and Docker distribution in the same change.

  VERIFY BEFORE DELETE.
    Legacy auth and roles are removable only after proving what still uses
    them. Existing database role names and SolidWorks add-ins matter more
    than grep results.

  MEASURE BEFORE OPTIMISE.
    Items 2.5 and 2.6 do not become coding tasks until profiling proves the
    current implementation is still materially hot.

  DATA MIGRATIONS MUST BE ADDITIVE AND REVERSIBLE.
    No destructive role/database/file migration. A failed migration may stop;
    it may not silently remove access or data.

  DO NOT WEAKEN THE HARDENED IMAGE FOR COMMUNITY USE.
    Community deployment must preserve non-root app execution, read-only
    filesystem where practical, tmpfs /tmp, no-new-privileges, dropped
    capabilities, authenticated Mongo, internal-only Mongo/Redis and the
    existing health/readiness behaviour.

  NEXTCLOUD TUNING IS CLOSED.
    N11 is architecture, not another resource-tuning pass. N9/N10 are only
    reconsidered if N11 design evidence makes them relevant.

  solidworks-addin/ STILL REQUIRES REAL SOLIDWORKS ACCEPTANCE.
    Do not claim compat code can be deleted based only on server tests.

  THERE IS ONE AUTHENTICATION MODEL AND ONE ROLE MODEL. Do not add a second
    "compatibility" path for anything. Both existed here, both were default-on,
    and both were removed in one day once someone looked: the role bypass
    granted every permission in the registry to a role name, and compat mode
    let an application generate its own signing key. A compatibility path is
    not a smaller version of a feature - it is a second implementation of the
    security-critical one, kept where nobody tests it.

  A BACKUP IS NOT A BACKUP UNTIL IT HAS BEEN RESTORED.
    Carried forward because it has already cost this project twice: four
    consecutive backups were silently empty past a guard that only checked
    the file was non-empty, and eight deploy scripts - including
    backup-instance.sh and restore-instance.sh - were not executable, so
    the documented invocation failed outright. Check content, not exit codes.

  A4  BACKUP RETENTION AND CADENCE            DONE 2026-08-09 - see log
      Measured on mecs at 1.0 closure:
        deliverables.tar.gz   2.0 GB     99.9% of the backup
        mongo.archive.gz      2.3 MB     (27.1 MB uncompressed)
        live: 2.8 GB across 22151 files vs a 515 MB Mongo data dir
      The database is tiny; the engineering files are the entire cost.

      TWO PROBLEMS, both structural rather than incidental:
        - the daily job re-compresses all 2.8 GB every night even when not one
          file changed
        - there is NO retention policy at all. Nothing deletes anything, ever.
      At roughly 2 GB a night against ~14 GB free, the disk has about a week
      of runway, and a backup that runs out of space fails quietly.

      THE FIX FALLS OUT OF THE MEASUREMENT: split the cadences.
        - database: 2.3 MB compressed. Daily is free; hourly would be too.
        - deliverables: 2 GB that rarely all change. Weekly, or better an
          incremental rsync mirror that copies only what is new.
        - retention: keep N and drop the rest. Anything beats nothing.
      Deliberately not done on release day. It changes backup-instance.sh,
      which has already produced silent failures twice here.
      DONE WHEN: disk usage is bounded by policy, the database is captured at
      least daily, and a restore from the new layout has been proven on a
      disposable instance.
