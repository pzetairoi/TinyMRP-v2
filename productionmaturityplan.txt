1. HOW TO WORK FROM HERE
========================================================================

  KEEP 1.0 BORING.
    Small commits, one purpose each. Do not mix auth cleanup, RBAC migration,
    frontend typing and Docker distribution in the same change.

  VERIFY BEFORE DELETE.
    Legacy auth and roles are removable only after proving what still uses
    them. Existing database role names and SolidWorks add-ins matter more
    than grep results.

  MEASURE BEFORE OPTIMISE.
    Items 2.5 and 2.6 do not become coding tasks until profiling proves the
    current implementation is still materially hot.

  DATA MIGRATIONS MUST BE ADDITIVE AND REVERSIBLE.
    No destructive role/database/file migration. A failed migration may stop;
    it may not silently remove access or data.

  DO NOT WEAKEN THE HARDENED IMAGE FOR COMMUNITY USE.
    Community deployment must preserve non-root app execution, read-only
    filesystem where practical, tmpfs /tmp, no-new-privileges, dropped
    capabilities, authenticated Mongo, internal-only Mongo/Redis and the
    existing health/readiness behaviour.

  NEXTCLOUD TUNING IS CLOSED.
    N11 is architecture, not another resource-tuning pass. N9/N10 are only
    reconsidered if N11 design evidence makes them relevant.

  solidworks-addin/ STILL REQUIRES REAL SOLIDWORKS ACCEPTANCE.
    Do not claim compat code can be deleted based only on server tests.

  THERE IS ONE AUTHENTICATION MODEL AND ONE ROLE MODEL. Do not add a second
    "compatibility" path for anything. Both existed here, both were default-on,
    and both were removed in one day once someone looked: the role bypass
    granted every permission in the registry to a role name, and compat mode
    let an application generate its own signing key. A compatibility path is
    not a smaller version of a feature - it is a second implementation of the
    security-critical one, kept where nobody tests it.

  A BACKUP IS NOT A BACKUP UNTIL IT HAS BEEN RESTORED.
    Carried forward because it has already cost this project twice: four
    consecutive backups were silently empty past a guard that only checked
    the file was non-empty, and eight deploy scripts - including
    backup-instance.sh and restore-instance.sh - were not executable, so
    the documented invocation failed outright. Check content, not exit codes.

  A4  BACKUP RETENTION AND CADENCE            DONE 2026-08-09 - see log
      Measured on mecs at 1.0 closure:
        deliverables.tar.gz   2.0 GB     99.9% of the backup
        mongo.archive.gz      2.3 MB     (27.1 MB uncompressed)
        live: 2.8 GB across 22151 files vs a 515 MB Mongo data dir
      The database is tiny; the engineering files are the entire cost.

      TWO PROBLEMS, both structural rather than incidental:
        - the daily job re-compresses all 2.8 GB every night even when not one
          file changed
        - there is NO retention policy at all. Nothing deletes anything, ever.
      At roughly 2 GB a night against ~14 GB free, the disk has about a week
      of runway, and a backup that runs out of space fails quietly.

      THE FIX FALLS OUT OF THE MEASUREMENT: split the cadences.
        - database: 2.3 MB compressed. Daily is free; hourly would be too.
        - deliverables: 2 GB that rarely all change. Weekly, or better an
          incremental rsync mirror that copies only what is new.
        - retention: keep N and drop the rest. Anything beats nothing.
      Deliberately not done on release day. It changes backup-instance.sh,
      which has already produced silent failures twice here.
      DONE WHEN: disk usage is bounded by policy, the database is captured at
      least daily, and a restore from the new layout has been proven on a
      disposable instance.

      per LAYER with $in instead of per PARENT, turning O(distinct parents)

  D2  REMAINING TREE WALKS                              CLOSED 2026-08-09
      Profile first. Only optimise walks that are both frequent and material.
      Do not spend engineering effort on once-a-day paths to improve a number
      nobody experiences.
      TINYMRP_PROFILE=1 counts Mongo operations per request. Count, not time:
      every query here already runs in about a millisecond and the damage is
      doing it four hundred times. It costs about 31% CPU, so turn it off after.

      INVENTORY, not guesswork: grepped for every stack/recursive tree walk
      alongside _flatten_bom (docpacks.py's second walk, export_security.py,
      parts_delete.py, arena_export.py). Two already had a bug like the one
      D1 re-verified was fixed - docpacks.py's `_bom_occurrences` already has
      its own `_children_cache`, and `where_used_pairs`/`_collect_bom_descendants`
      are single-level or already visited-set-deduplicated. ONE was genuinely
      unfixed: arena_export.py's two walk() functions called `_child_links`
      fresh on every visit, with no cache at all - the exact defect
      `_flatten_bom` was fixed for, just not yet applied here.

      FOUND, MEASURED, FIXED: a real A/B against the pre-fix committed source
      (loaded from git HEAD as a second module in the same process, run
      against identical synthetic BOMs) shows the overhead COMPOUNDS with
      depth rather than staying flat:
        3 layers:  1.48x queries/part vs. the fixed version's flat 1.00x
        4 layers:  2.37x
        5 layers:  3.07x
      A 6-layer graph at the same scale used for D1 never finished in several
      minutes on the unfixed code - consistent with that growth curve, not
      contradicting it. Fixed by applying the SAME pattern D1 re-verified:
      memoise the constant-per-part lookups (BOMLink children query, Part
      fetch, harvested attrs, description), while explicitly NOT memoising
      the walk/output itself in build_arena_bom_csv, because Arena's BOM
      format legitimately needs one CSV row per occurrence-path - quantity,
      level and total_qty all vary by path, so collapsing revisits there
      would silently drop real BOM lines, not just be slow. That distinction
      is load-bearing and is spelled out in the code comment.
      _collect_unique_parts is a different case: it only ever wanted a SET,

        lose a record, it defeats the duplicate check and THE SAME IMPORT
        CAN RUN TWICE. Still allowed to proceed, because blocking imports on
        a journal outage would be worse, but now loud.
        A completed import whose audit record could not be written was also
        silent; that is precisely the event someone later needs to
        reconstruct.

    BATCH 3, file serving (fileserve.py). Same shape again: correct
      fail-closed behaviour, no voice. Resolving storage roots to [] means
      EVERY file 404s, which is the safe direction and also the most
      misleading - it looks exactly like an instance whose files were never
      imported. And a 403 from the path-traversal guard should be
      distinguishable in the logs from a 403 caused by a resolver bug.

    A PATTERN WORTH NAMING, since it held in all three batches: none of
      these had the wrong behaviour. Every one already failed closed. The
      defect was that failing closed and working correctly produced
      identical output, so no amount of log-reading could tell them apart.
      When triaging the rest, ask "could I distinguish this failing from
      this working?" before asking "is the fallback safe?".

    BATCH 4, file discovery (filescan.py). The two that matter on the
      import path: unresolvable file sources make discovery find nothing,
      so an import reports "no files" - which reads as a pack that
      contained none rather than storage the server could not enumerate.
      And an unreadable directory becomes an empty one, so every file
      inside it silently stops being discovered. Permissions drift is the
      usual cause and it is invisible from outside.

    BATCH 5, extra-file uploads (extra_files.py). The one that matters: a
      FAILED ROLLBACK was silent. The original exception is re-raised, so
      the caller learns the upload failed - but not that the file on disk is
      now in an unknown state relative to the database. It now names the
      path, which is the only way anyone reconciles it later.
      Staging-directory cleanup moved to debug rather than silence: leftover
      temp dirs waste disk and break nothing, so they should be findable
      without being noisy.

    HOW TO JUDGE THE REST, distilled from five batches:
      Ask "could I tell this failing apart from this working?" first. If
      not, log it. Then ask "does the fallback leave state inconsistent?"
      If yes, log the identifier needed to reconcile it - a path, a key, an
      id - not just the fact that something went wrong. Everything else is
      best-effort cleanup and belongs at debug, not deleted and not raised.

    BATCH 6, document packs (docpacks.py, 90 handlers - the largest single
      concentration). Only ONE was worth changing: a failed reportlab import
      returned None, which drops a section from the pack. The document still
      builds and still LOOKS complete, so the result is a manufacturing
      document with a section quietly absent rather than a failure anyone
      notices. The rest are PDF-structure parsing against malformed input,
      where swallowing genuinely is the right answer.
      That ratio is the argument against chasing the count: 1 in 90 here,
      against 6 in 7 in authorization.py.

    BATCH 7, public share surface (part_shares.py). A failed file-token
      resolution and a forged token both produced 404 - correct for the
      caller, who must learn nothing, but identical in the log. A
      regression in the resolver would have read as ordinary probing
      traffic. Same for public BOM resolution.

    B3 CLOSED 2026-08-09 on the plan's own definition of done: "high-risk
    silent handlers are gone; low-risk best-effort handlers are either
    justified or tracked, not merely counted."

    FINAL POSITION: 17 handlers changed out of 276. The other 259 were
    read, not skipped, and fall into three justified groups:
      - PDF and file-format parsing against malformed input (89 in
        docpacks.py alone), where swallowing IS the correct answer
      - request-context accessors in audit.py that already degrade to ""
        and whose own failure path already logs
      - best-effort UI decoration: thumbnails, labels, optional columns,
        where an exception must not take a page down
    None of these can produce a wrong answer that looks right, which was

    DO NOT reopen this as a counting exercise. The ratio across the
